SafeLine WAF は、公開している Web アプリケーションの手前に置き、インターネットとオリジンサーバの間を流れる HTTP トラフィックを検査する自己ホスト型の WAF です。nginx をベースにしたリバースプロキシとして動作します。この記事では「WAF で HTTPS サイト用の SSL 証明書をどのように登録するのか」という疑問に対して、公式ドキュメントに書かれている範囲だけを使って、実際の導入手順と確認ポイントを整理します。

はじめに、重要な前提を確認します。提供された公式ドキュメントには、証明書のアップロード画面、ファイル形式、チェーン証明書の並び順、更新手順についての記述はありません。ドキュメントに明記されているのは、保護対象が HTTPS のアプリケーションである場合に「SSL オプションをチェックする」ことだけです。したがって本記事は、証明書アップロード機能の存在を約束するものではなく、ドキュメントに沿った導入と設定のチェックリストとして読み進めてください。公式ドキュメントは https://docs.waf.chaitin.com/en/home です。

## 導入手順

1. ホストの要件を確認する
SafeLine を動かすホストには、Linux、x86_64 または arm64、Docker 20.10.14 以上、Docker Compose 2.0.0 以上、CPU 1 コア以上、メモリ 1GB 以上、ディスク 5GB 以上、ssse3 命令に対応した CPU が必要です。確認コマンドは、uname -m（アーキテクチャ）、docker version、docker compose version、free -h（メモリ）、df -h（ディスク）、/proc/cpuinfo のプロセッサ確認と lscpu での ssse3 確認です。証明書の話に入る前に、まずこの前提を満たしていることを確かめます。

2. 文書化された方法だけでインストールする
推奨される自動デプロイは root が必要で、次のコマンドを使います。
bash -c "$(curl -fsSLk https://waf.chaitin.com/release/latest/manager.sh)" -- --en
完了後に Web コンソールへアクセスします。手動デプロイでは、必要なら Docker を導入し、/data/safeline を作成して compose.yaml を配置し、.env を書き、検出器と管理用のトークン、16 文字の英数字の AES キーを生成し、パーミッションを制限し、必要なリソースディレクトリを作成して、docker compose up -d で起動します。ARM サーバでは ARCH_SUFFIX を -arm にして ARM 用の Postgres イメージを使います。なお、ARM 版は Pro ライセンスが必要で、Personal Edition は ARM 非対応とされています。このライセンスの注意はプラットフォームに関するもので、証明書の登録とは無関係です。

3. コンソールを開き、最初の管理者を作成する
ブラウザで https://<safeline-ip>:9443/ を開きます。続いて docker exec safeline-mgt resetadmin を実行し、表示される初期ユーザー名とパスワードを控えてログインします。ここで注意が必要です。9443 番ポートのコンソール TLS は、公開サイト用の証明書ではありません。ドキュメントには、管理ポートの証明書をアプリケーションのリスナーが再利用するとは書かれていません。

4. 3 つの必須フィールドでアプリケーションを追加する
Applications ページで Add Application を選びます。Domain に公開ホスト名、Port に SafeLine が待ち受けるポート（HTTPS サイトなら 443 が例）、Upstream にオリジンアプリケーションの実際のアドレスを入力します。HTTPS のアプリケーションなので、SSL オプションをチェックします。ここで証明書のアップロード欄が必要なのにコンソール内に見つからない場合は、いったん停止してください。これらの資料は、独自の nginx スニペットや、キー用のボリュームマウントといった回避策を認めていません。

5. アプリケーション登録が済んでから名前解決を切り替える
登録した Domain を、SafeLine が動くサーバの IP アドレスに解決させます。DNS がまだオリジンを向いていると、クライアントはリバースプロキシを経由しないため、SSL オプションは経路を変えられません。

6. 公開されているテストケースで検査を証明する
証明書の想定ではなく、実際の検査で確認します。アプリケーションガイドには、SQL インジェクション、XSS、パストラバーサル、コードインジェクション、XXE のサンプルクエリが示されており、ブロックページが表示されれば攻撃を防御できたことになります。さらに Web コンソールの攻撃リストを開き、該当イベントの詳細を確認します。たとえブラウザの鍵アイコンが表示されても、それは攻撃リストの確認の代わりにはなりません。

## 失敗事例：DNS の向き先がオリジンのまま

ある担当者は、証明書の設定を探す前に「サイトへ HTTPS でアクセスできているから問題ない」と判断しました。ところが、DNS のレコードはオリジンサーバのままだったため、クライアントは SafeLine を一切経由しておらず、SSL オプションも WAF の検査も機能していませんでした。攻撃リストには何も記録されず、原因が判明するまで数日を無駄にしました。教訓は、登録したドメイン名が確実に SafeLine サーバの IP を向いていることを、実際のリゾルバで確認してからテストする、ということです。

## HTTPS に依存する前のチェックリスト

- 識別: Domain の値は、クライアントが要求するホスト名と一致しているか。ドメイン名、ホスト名、IP アドレスの指定は可能ですが、HTTPS のホスト名と IP リスナーは運用上異なる選択です。
- リスナー: Port は SafeLine が待ち受けるポートです。通常の HTTPS サイトなら 443 が該当します。SSL オプションのチェックは HTTPS アプリ向けに文書化されていますが、PEM のアップロード、チェーン選択、パスフレーズ設定は文書化されていません。
- オリジン: Upstream は SafeLine が検査済みトラフィックを転送する先です。2 つ目の公開リスナーではありません。SafeLine ホストから到達できる状態を保ちます。
- 切り替え: アプリケーション保存後、DNS は SafeLine サーバを向いていなければなりません。新しいレコードを参照できるリゾルバでテストします。
- 範囲: レート制限、CAPTCHA、認証チャレンジ、動的保護は製品紹介に含まれる別機能です。証明書ワークフローが無いことの代用にはしないでください。
- 証跡: 切り替え後、文書化された攻撃サンプルを 1 つ実行し、ブロックページと攻撃リストの詳細表示を確認します。リクエストが SafeLine に届いていなければ、証明書設定を探す前に DNS かリスナーを修正します。

## まとめ

証明書のアップロード画面やキーのエクスポート、自動更新が必須の設計であれば、この 3 ページの資料だけではその設計を承認できません。本番切り替えの前に、最新のドキュメントから不足している手順を収集してください。現時点でドキュメントが支持する成果は、正しく導入されたリバースプロキシ、Domain・Port・Upstream を入力し HTTPS アプリに対して SSL オプションをチェックしたアプリケーションエントリ、そして SafeLine ホストに向けた DNS です。
