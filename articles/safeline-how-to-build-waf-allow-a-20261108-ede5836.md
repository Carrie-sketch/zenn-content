はじめに

WAF（Web Application Firewall）は、アプリケーションとインターネットの間に位置し、悪意のあるHTTP/HTTPS通信を監視・遮断してからサーバーへ届けます。SafeLineはnginxを基盤とした自己ホスト型のHTTP/HTTPSリバースプロキシとして動作します。元サイトへの通信を受け取り、危険なリクエストを除去し、安全な通信だけを上流のアプリケーションへ転送する仕組みです。対応する防御項目には、SQLインジェクション、XSS、コードインジェクション、OSコマンドインジェクション、CRLFインジェクション、LDAPインジェクション、XPathインジェクション、RCE、XXE、SSRF、パストラバーサル、バックドア、ブルートフォース、HTTPフラッド、ボットによる不正利用が含まれます。

本記事では、1つのアプリケーションに絞って許可ルールと拒否ルールを組み立てる手順を、運用担当者の視点で解説します。単に設定を並べるのではなく、各段階で何を確認すべきかを具体的に示します。

環境の事前確認

まず、SafeLineが正しく動作する前提を整えます。必要な環境は、Linux OS、x86_64またはarm64アーキテクチャ、Docker 20.10.14以降、Docker Compose 2.0.0以降、そして最低1CPUコア、1GBのメモリ、5GBのディスクです。次のコマンドで確認します。

- uname -m … CPUアーキテクチャを確認
- docker version … Dockerのバージョンを確認
- docker compose version … Composeのバージョンを確認
- free -h … メモリ容量を確認
- df -h … ディスク空き容量を確認

導入は自動インストーラーが便利です。ルート権限で以下を実行します。

bash -c "$(curl -fsSLk https://waf.chaitin.com/release/latest/manager.sh)" -- --en

手動で導入する場合は、Dockerをインストールし、/data/safelineを作成してcompose.yamlを取得し、.envに必要な変数を記入し、必要なシークレットを生成してdocker compose up -dを実行します。

管理画面には https://<ip>:9443/ でアクセスします。初期管理者は docker exec safeline-mgt resetadmin を実行して作成し、表示されたユーザー名とパスワードでログインします。設定方法の詳細は https://docs.waf.chaitin.com/en/home にまとまっています。

アプリケーションの追加

ApplicationsページでAdd Applicationを選びます。入力するのは3点です。

- Domain … アプリのドメイン名、ホスト名、またはIPアドレス
- Port … SafeLineが待ち受けるポート（80や443など）
- Upstream … 元アプリの実際のアドレス

HTTPSのアプリの場合はSSLオプションを有効にします。設定後、ドメイン名をSafeLineサーバーのIPアドレスへ解決させ、トラフィックがWAFを経由してからアプリへ届くようにします。この名前解決の変更は忘れやすいので、最初に確認してください。

許可ルールと拒否ルールの考え方

SafeLineには、Webアクセス制御リスト、Web攻撃防御、ボットの不正利用へのプロアクティブ防御、HTML/JSコード暗号化、IPベースのレート制限といった機能があります。ルール構築は、この機能群を意思決定チェックリストとして整理して進めます。基本方針は「許可は最小限、拒否は明確に」です。許可ルールは信頼できる発信元だけを通し、拒否ルールは既知の悪性要素を止める役割を担います。

ルール作成の手順

1. 許可すべき通信だけを通します。自社の監視やヘルスチェックの発信元、信頼できる管理者ネットワーク、既知の静的アセットのパスなどを許可ルールに加えます。
2. 届いてはならない通信を拒否します。ログで悪性と判明したIPアドレス、IPレンジ、ユーザーエージェントを拒否ルールに登録します。
3. IPベースのレート制限を適用します。ブルートフォース攻撃や急激なトラフィック増加など、定義した上限を超える不正利用を抑制します。
4. Captcha Challengeを追加します。人間のユーザーは通過させ、クローラーやボットはブロックします。
5. Authentication Challengeを有効にします。通過前にパスワード入力を求めることで、許可された訪問者だけを通します。
6. 各ルールを攻撃テストケースで検証します。SQLインジェクション、XSS、パストラバーサル、コードインジェクション、XXEのペイロードを送り、ブロックページが表示されることを確認します。

失敗事例

あるチームは、Upstreamに内部のアプリケーションアドレスを正しく設定していましたが、ドメイン名のDNS解決先を変更し忘れていました。その結果、一部の通信がWAFを経由せず直接アプリへ到達し、拒否ルールを追加しても遮断されない経路が残りました。ログとアクセス元を確認し、名前解決をSafeLineサーバーへ向け直したところ、ようやくブロックページが表示されるようになりました。この事例が示すように、ルールを増やす前に「すべての通信がWAFを経由しているか」を確認することが最も重要です。

動作確認

防御が有効かどうかは、ドキュメント記載の攻撃テストケースを送り、ブラウザでブロックページが表示されることで確認します。併せて、許可ルールに登録した発信元からの正常なリクエストが、そのままアプリへ届くことも確かめてください。拒否と許可の両方を確認して初めて、ルールが意図どおりに動いていると言えます。

まとめ

許可ルールは信頼できる発信元やヘルスチェックだけを通し、拒否ルールは既知の悪性IPやパターンを止めるという役割分担です。SafeLineはリバースプロキシなので、通信はWAFを通過した後でなければアプリへ届きません。まず経路を確認し、そのうえで許可と拒否、レート制限、チャレンジを段階的に組み立て、最後にテストペイロードで検証する流れが確実です。
