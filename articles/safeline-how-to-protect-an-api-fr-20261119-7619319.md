API のログインがせいこうしても、そのユーザーにすべてのデータをみせてよいわけではありません。たとえば `/accounts/1842/invoices/7` の `1842` を `1843` にかえたとき、べつのアカウントのデータがかえってくるなら、BOLA（Broken Object Level Authorization）のうたがいがあります。BOLA は、リクエストしたオブジェクトへのアクセスを、そのつどたしかめていないことでおこります。

このガイドでは、SafeLine WAF を API のまえにおき、アプリのアクセスチェックとあわせてうんようするてじゅんをまとめます。SafeLine はセルフホストのリバースプロキシとして HTTP トラフィックをフィルタリングし、ゆるされたリクエストをアプリへわたします。ただし、ID だけをみてデータのもちぬしやテナントのルールをはんだんすることはできません。オブジェクトへのアクセスをゆるすかどうかは、アプリでかならずたしかめます。

## みじかいしっぱいケース

ある API では、トークンがただしければ `/documents/{documentId}` をよめるつくりになっていました。テストユーザー A がユーザー B の documentId をいれると、HTTP 200 とともに B のデータがかえりました。ログインのチェックはありましたが、ドキュメントのもちぬしとテナントのチェックがぬけていたのです。

このケースでは、アクセスのスピードをおとしても、さいしょの 1 リクエストでデータがもれることがあります。アプリでアクセスをことわるしくみと、れんぞくした ID のためしうちをおさえるしくみのりょうほうがひつようです。

## 1. エンドポイントごとにルールをかく

まず、だれが、どのオブジェクトに、なにをしてよいかをかきだします。`/users/{userId}/documents/{documentId}` なら、URL の userId がトークンとあっているかだけでなく、documentId がそのユーザー、またはアクセスをゆるされたテナントにぞくしているかをたしかめます。

- GET、POST、PATCH、DELETE をそれぞれチェックする。
- すうじの ID と、ランダムにみえる ID のりょうほうをためす。
- ネストした URL、バッチ、エクスポート、GraphQL、RPC のけいろもあらいだす。
- ことわるときの HTTP 403 または 404 など、API としてのふるまいをきめる。

ID があてにくいことを、アクセスチェックのかわりにしないでください。アプリのコードにルールをおき、API をかえるたびにレビューします。

## 2. SafeLine をおくホストをチェックする

デプロイまえに、Linux、x86_64 または arm64、Docker 20.10.14 いこう、Docker Compose 2.0.0 いこうをチェックします。リソースは、すくなくとも CPU 1 コア、メモリ 1 GB、ディスク 5 GB がひつようです。

インストールは、こうしきドキュメントのてじゅんにそってすすめます。マニュアルでセットアップするなら、`/data/safeline` をつくり、ドキュメントにある Compose ファイルと、ひつようなかんきょうへんすうをそろえます。トークンやキーをつくり、`.env` のパーミッションを `600` にしてから `docker compose up -d` でたちあげます。さいしょの admin アカウントは、ドキュメントの `resetadmin` コマンドでとりだします。

ダッシュボードの URL は `https://<ip>:9443` です。ここへアクセスできるひとをしぼり、ポリシーをかえられるひとをきめておきます。トークンやデータベースのパスワードはシークレットとしてあつかい、データディレクトリのディスクあきもみはります。

## 3. API をプロキシにつなぎ、けいろをたしかめる

SafeLine の Web Admin Console で Applications をひらき、API のドメイン、リッスンするポート、アップストリームをセットします。API のホストネームが SafeLine サーバーへむくようにし、リクエストがプロキシをとおってアプリへとどくことをたしかめます。ネットワークのつくりにあわせて、オリジンへインターネットからちょくせつアクセスできるぬけみちもふさぎます。

テストには、べつべつのテナントにいるアカウント A と B をつかいます。まず A のトークンで A のデータをよみます。つぎにトークンはそのままにして、ID だけを B のものへかえます。ここでアプリがアクセスをことわることがチェックポイントです。WAF がとめたというけっかだけで、アプリのルールがただしいときめないでください。

SafeLine のアタックリストとリクエストのしょうさいもひらき、ブロックしたトラフィックをたどれるかたしかめます。

## 4. ID のためしうちをレートでおさえる

オブジェクトをさがす API、ログイン、トークンのリフレッシュ、エクスポート、データをかえる API には、それぞれにあったレートリミットをかんがえます。SafeLine には、DoS トラフィック、ブルートフォース、アクセスのきゅうぞうなどにむけたレートリミットがあります。ひとによるチェックがなじむフローでは、CAPTCHA やにんしょうチャレンジもせんたくしになります。

しきいちは、ふだんのアクセスやバッチ、パートナーのれんけいをみてからきめます。403 が 1 かいでたことだけでブロックせず、おなじユーザー、トークン、IP アドレス、User-Agent が、ID をかえながらくりかえしアクセスしているかをみます。スマートフォンのアプリやサーバーどうしの API れんけいでも、ただしいクライアントがうごきつづけるかをたしかめてください。

## 5. WAF とアプリのログをつなぐ

アプリには、ユーザー、テナント、オブジェクト ID、ルート、HTTP メソッド、IP アドレス、User-Agent、レスポンスのステータス、correlation ID をのこします。SafeLine のきろくとアプリのアクセスチェックのログ、データベースのアクセスログをつきあわせられるようにします。

ちゅういしたいのは、「ログインせいこう → ID をすばやくへんこう → 403 や 404 がれんぞく → べつテナントのデータに 200」というながれです。アラートがでたら、リクエストとアプリのはんだんをほぞんし、アクセスされたオブジェクトをしらべます。ひつようにおうじてトークンをむこうにし、もれたデータとそのきかんをしらべて、インシデントのたんとうしゃへつなぎます。

## 6. しゅうせいごとにアクセスのテストをくりかえす

さいごに、すべてのエンドポイントと HTTP メソッドで、おなじテナント、べつテナント、そんざいしないオブジェクト、きげんぎれトークン、バッチのケースをためします。バッチでは、アクセスできる ID とできない ID をまぜたケースもチェックします。

アプリがアクセスできないオブジェクトをかえさないこと、SafeLine でかんれんするトラフィックをしらべられること、ただしいクライアントがうごくこと、オリジンへのぬけみちがないことをたしかめます。みつけたぬけはテストにくわえ、つぎの API へんこうでもおなじしっぱいをふせぎます。SafeLine でためしうちやじどうアクセスをおさえながら、オブジェクトごとのアクセスルールをアプリでまもることが、BOLA たいさくのきほんです。
