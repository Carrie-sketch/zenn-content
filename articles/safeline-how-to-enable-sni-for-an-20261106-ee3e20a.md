SafeLineはWebアプリケーションの前に置かれ、HTTP/HTTPSトラフィックを検査して悪性リクエストを遮断する自己ホスト型WAFです。内部ではnginxベースのリバースプロキシとして動作し、検査後に残った通信を本来のアプリケーションへ転送します。

SNI（Server Name Indication）はTLS拡張のひとつです。ハンドシェイク時にクライアントがホスト名を送ることで、複数の証明書を持つサーバーが適切な証明書を選べるようにします。これはTLS一般の挙動であり、それ自体が製品の設定項目として用意されているわけではありません。ここでは、ドキュメント化された操作だけを使い、上流のSNIに関する疑問を運用として解決する手順を整理します。管理画面は https://<ip>:9443 、公式ドキュメントは https://docs.waf.chaitin.com/en/home です。

## 導入とサイトの接続

1. ホスト要件を確認します。対象はx86_64またはarm64のLinuxで、Docker 20.10.14以上、Docker Compose 2.0.0以上が必要です。最小環境はCPU 1コア、メモリ1GB、ディスク5GB、CPUはssse3対応です。uname -m、docker version、docker compose version、cat /proc/cpuinfo、free -h、df -h、lscpu などで確認します。

2. デプロイガイドの自動インストールコマンドを使う場合はroot権限で実行します。bash -c "$(curl -fsSLk https://waf.chaitin.com/release/latest/manager.sh)" -- --en を実行し、完了後にWebコンソールへ進みます。

3. 手動で入れる場合は、Dockerがなければ導入し、/data/safeline を作成してデプロイガイドのリリースURLからcompose.yamlを取得し、SAFELINE_DIR、IMAGE_TAG、MGT_PORT、POSTGRES_PASSWORDなどを含む.envを用意します。検知器と管理用のシークレットはガイドのコマンドで生成し、.envに書き込んで chmod 600 .env とします。必要なディレクトリと権限を整え、docker compose up -d で起動します。起動には数分かかることがあります。

4. https://<safeline-ip>:9443/ を開きます。docker exec safeline-mgt resetadmin を実行し、表示される管理者ユーザー名とパスワードを控えます。

5. ログインして Applications を開き、Add Application を選びます。元のアプリのドメイン、ホスト名、またはIPを入力し、SafeLineが待ち受けるポートを設定します。HTTPSアプリなら SSL をチェックします。通常は443ですが、実際に割り当てたポートを使ってください。Upstream には元のアプリの実際のアドレスを設定します。ここが検査後の転送先です。

6. 公開するドメインをSafeLineサーバーのIPに解決します。クライアントはWAFを経由して保護対象アプリへ到達するようにします。

7. サンプルドメインを自分のドメインに置き換えて、SQLインジェクション、XSS、パストラバーサル、コードインジェクション、XXEの各検証リクエストを送ります。ブロックページが表示されたら遮断成功です。攻撃リストを開いて詳細を確認すれば、フィルタリングが動いている証拠になります。ただし、これは上流側でどの証明書が選ばれたかを証明するものではありません。

## SNIが設定項目にない場合のチェックリスト

8. 切り替え前に4つの値を記録します。公開ドメイン、待受ポート、SSLのチェック有無、Upstreamの正確な文字列です。これらを、クライアントが期待するホスト名で直接接続したときにオリジンが提示する証明書と比較します。証明書がその名前と一致する専用オリジンは、共有HTTPSリスナーより単純な構成です。

9. UpstreamがIPの場合、または複数のHTTPSサイトが同じオリジンアドレスを共有する場合は、オリジンの運用者にTLSリスナーがホスト名で証明書を選ぶかを確認します。ここがSNIの判断点です。アプリケーション追加ガイドには、上流へ独自のServer Nameを送るコンソール項目は記載されていません。ドキュメントにない設定を勝手に足したり、未公開の手順を正式な連携として扱ったりしないでください。ドキュメント化された Domain、Port、SSL、Upstream で表現できないホスト名が必要なら、そのレイアウトに収まる構成へ変更するか、切り替えを延期します。

10. 3つのアドレスを別々に確認します。DNSはSafeLineホストを指すこと、待受ポートはSafeLine上のポートであって必ずしもオリジンのポートではないこと、UpstreamはオリジンのアドレスであってSafeLineのアドレスではないこと、を確認します。SafeLine自身をUpstreamにするとループします。保護対象ドメインで通常ページを開き、続けてドキュメント化された攻撃URLを1つ試して、攻撃リストに新しい行が増えることを確認します。

## 失敗例:共有HTTPSリスナーでの証明書不一致

ある共有ホスティングのオリジンは、同じIPで複数サイトをTLS終端し、SNIで証明書を選んでいました。UpstreamにIPだけを設定して切り替えると、上流へのハンドシェイクで既定の証明書が返り、ブラウザに証明書の警告が出ました。攻撃の遮断自体は動いていましたが、正しいサイト証明書を提示できませんでした。この場合、管理画面の上流SNIトグルを探すのではなく、証明書名とUpstreamの値を突き合わせ、オリジンが名前ベースのHTTPSホスティングかどうかを先に確認するのが正しい対応です。必要な上流サーバー名を既存の項目で表現できないなら、未文書の回避策ではなく、対応可能な構成に揃えてから切り替えます。

## よくある疑問

アプリケーション追加ガイドに上流SNIのトグルはありますか。いいえ。記載されているのは Domain、Port、HTTPSアプリ用のSSL、Upstream だけです。オリジンへ送るServer Nameを個別に指定する項目はありません。ホスト名と証明書は、これらの項目に合わせて設計します。

SSLはいつチェックしますか。SafeLineがHTTPSアプリとして待ち受ける場合にチェックします。公開する待受ポートは443など、割り当てた値にします。

Upstreamには何を入れますか。元のアプリの実際のアドレスです。検査後に転送する先であって、SafeLineサーバーのアドレスを入れると自分へ戻ってループします。

フィルタリングが動いていることはどう確認しますか。自分のドメインへドキュメント化された検証リクエストを送り、ブロックページと攻撃リストの行の両方を確認します。

証明書が1つのホスト名にしか一致しない場合はどうしますか。オリジン側の制約として扱います。証明書名、Upstreamの値、名前ベースのHTTPSホスティングの有無を先に確認します。隠れたプロキシ設定として探すのではなく、項目で表現できる構成に揃えるのが確実です。
