セルフホスト型の WAF（Web Application Firewall）である SafeLine は、アプリケーションの前面にリバースプロキシとして配置し、HTTP／HTTPS の通信を検査して不正なリクエストを遮断する。SQL インジェクションや XSS、RCE、SSRF、パストラバーサル、総当たり攻撃、ボットの悪用などへの防御を担う。

SafeLine の設定や実行時のデータは、セットアップ時に作成したディレクトリに保存される。公式のアンインストール手順は短いが破壊的である。具体的には「compose プロジェクトを停止し、そのディレクトリを削除する」という二段構えになる。本稿では、公開されている手順だけを使い、ディレクトリの特定方法、中身、削除時の注意点を整理する。

## 削除前に押さえるチェック項目

最初に、どのディレクトリを消すのかを確定する。マニュアルセットアップの例では `/data/safeline` が作業ディレクトリになるが、すべてのホストがこのパスを使うとは限らない。`.env` ファイルが存在すれば、その中の `SAFELINE_DIR` が実際のパスを記録している。ここを読み、推測でパスを決めないこと。

次に、管理画面の URL を確認しておく。デフォルトでは `https://<IP>:9443` でダッシュボードにアクセスできる。この URL がまだ生きているかを見れば、対象インスタンスが稼働中かどうかを判断できる。

続いて、オリジン（保護対象のアプリケーション）への経路を確認する。SafeLine はドメインを自身のサーバに向けて解決し、検査済みのトラフィックを上流へ転送する。SafeLine を止めた後は、その解決先に稼働中のリスナーがなくなる。DNS やルーティングの変更は自分の運用プロセスで行う必要があり、公式に公開された切り替えコマンドは存在しない。

最後に、`.env` に含まれるシークレット（Postgres のパスワードや各種トークン）を保持するか判断する。削除は不可逆なので、自社の保持ポリシーに従って必要なものだけを控える。

## アンインストール手順

1. `<safeline-directory>` を特定する。マニュアルインストールの既定は `/data/safeline`。カスタムセットアップなら `SAFELINE_DIR` の値を用いる。
2. クライアントがオリジンへ到達する経路を計画する。ドメインの解決先を変更するなど、SafeLine を経由しない導線を用意する。
3. 対象ディレクトリへ移動する: `cd <safeline-directory>`
4. スタックを停止する: `docker compose down`
5. データディレクトリを削除する: `rm -rf <safeline-directory>`
6. パスが消えたことを確認する。この後に `docker compose up -d` や `docker exec safeline-mgt resetadmin` を実行しないこと。前者はサービスを再起動し、後者は管理者アカウントをリセットするため、後片付けではなく導入やログインの手順である。

停止と削除は別の作業である。`docker compose down` だけでは `rm -rf` は実行されない。

## 失敗例: 停止だけして削除を忘れる

ある担当者が「アンインストールした」と報告したが、実際に実行したのは `docker compose down` だけだった。ディレクトリはそのまま残っており、設定やトークン、ローカルの Postgres ファイルがディスク上に存続した。後日、容量調査で `/data/safeline/resources/postgres/data` が残っているのが見つかり、改めて `rm -rf` を実行する羽目になった。停止と削除を一つの作業と混同しないことが重要である。

## 削除がカバーするもの・しないもの

ディレクトリ内には `compose.yaml`、`.env`、リソース用のパスが配置される。`.env` は `chmod 600` で保護され、Postgres のパスワードやトークンを含み得る。Postgres のデータは `resources/postgres/data` に用意される。ディレクトリを削除すると、compose プロジェクトとともにローカルの管理画面の状態も失われる。

ただし、Docker と Docker Compose はホスト側の依存関係として残る。アンインストール手順には Docker の削除は含まれない。

また、セットアップでは `/data/safeline/resources/run/safeline.sock` へのシンボリックリンクを `/var/run/safeline.sock` に張る手順がある。これはデータディレクトリの外にある。公式の削除手順にはこのリンクが含まれていないため、`rm -rf` の後に自分で確認し、必要なら通常のホストメンテナンスとして対処する。自動的に消えるとは考えないこと。

## よくある疑問

**`docker compose down` でデータディレクトリは消えるか。**

消えない。公式ガイドは `docker compose down` と `rm -rf <safeline-directory>` を別コマンドとして記載している。設定やトークン、ローカル Postgres を破棄したいときだけ削除を実行する。

**セットアップをカスタムした場合、どのディレクトリを消すか。**

自分が作成した SafeLine 用のディレクトリを消す。推測した既定値を使わない。マニュアル例は `/data/safeline` で、`SAFELINE_DIR` に記録される。`manager.sh` で始めた場合も実体はディスク上にあるため、削除前にホスト上でパスを確認する。

**この手順で Docker はアンインストールされるか。**

されない。要件は Docker 20.10.14 以上と Docker Compose 2.0.0 以上であり、アンインストールは SafeLine の compose プロジェクト停止とディレクトリ削除だけである。

**削除後も保護対象アプリケーションは同じ経路で動くか。**

動かない。訪問者は SafeLine サーバに解決されたドメインで到達し、SafeLine が上流へ転送するモデルである。プロキシを止めてディレクトリを消した後は、オリジンへの別経路が必要になる。この変更用の移行コマンドは公開されていない。

**ランタイムソケットは `rm -rf` に含まれるか。**

削除するディレクトリの内側にあれば含まれる。ただし `/var/run/safeline.sock` は SafeLine ディレクトリ内の `resources/run/safeline.sock` を指すシンボリックリンクであり、アンインストール手順では言及されない。`rm -rf` の後にこのリンクを確認し、通常のホストメンテナンスとして片付ける。

## まとめ

SafeLine のアンインストールは「compose プロジェクトの停止」と「データディレクトリの削除」の二段階である。削除前に `SAFELINE_DIR` で実パスを特定し、管理画面 `https://<IP>:9443` の稼働状態と、オリジンへの代替経路を確認する。`rm -rf` の前には、親ディレクトリ（たとえば `/data`）を対象にしていないか、そのパスのファイルを失ってよいか、アプリケーションの経路がこのプロキシに依存していないかを必ず確認する。停止だけで終わらせず、削除まで完了させることで、設定・トークン・ローカル DB を確実に取り除ける。
