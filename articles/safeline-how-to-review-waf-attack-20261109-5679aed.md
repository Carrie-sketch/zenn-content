ひとつの WAF でいくつものサイトをまもるとき、アタックイベントをながめるだけでは、どのアプリでなにがおきたのかをとりちがえがちです。とくに、インターネットからアクセスするポートと、バックエンドへつなぐポートをまぜると、しらべるべきサービスをまちがえます。

このガイドでは、SafeLine のアプリごとのドメインとポートをメモし、アタックリストと detail をつきあわせるやりかたをまとめます。ドメインとポートをまとめてグループにするしくみや、それぞれでイベントをしぼりこむフィルターは、もとのドキュメントではたしかめられていません。まずは、いまつかっているバージョンの UI にあるものだけでレビューをすすめましょう。

## 1. ホストのチェックをすませる

セットアップまえに、Linux、Docker 20.10.14 いこう、Docker Compose 2.0.0 いこうであることをたしかめます。リソースのめやすは CPU 1 コア、メモリ 1 GB、ディスク 5 GB です。アーキテクチャや CPU のインストラクションにもルールがあるため、リソースだけでチェックをおえないようにします。

ターミナルで `uname -m`、`docker version`、`docker compose version`、`free -h`、`df -h` をひとつずつうごかし、ドキュメントのセットアップルールとくらべてください。ARM では Pro ライセンスがいること、Personal Edition は ARM をサポートしないことにもきをつけます。

## 2. コンソールとサイトのアクセスさきをわける

ドキュメントのフローにそって SafeLine をセットアップします。オートセットアップには root がいります。セットアップごのダッシュボードは `https://<ip>:9443` です。ログインにつかうアカウントのクレデンシャルは、`docker exec safeline-mgt resetadmin` でとりだします。

ここでの 9443 はコンソールのポートです。サイトをうけつけるポートとは、メモのらんをわけてください。レビューのたびにコンソールのポートをサイトのポートとしてあつかわないための、ちいさくてもたいせつなチェックです。

## 3. ドメインとポートのペアをリストにする

コンソールの Applications から Add Application をひらくまえに、つぎのこうもくをメモします。

- アプリのなまえとオーナー
- パブリックなドメインまたはホストネーム
- SafeLine がリッスンするポート
- HTTPS をつかうかどうか
- Upstream のアドレスとポート
- チェックしたときのタイムスタンプ

Domain は、もとのアプリのドメイン、ホストネーム、または IP アドレスです。Port は SafeLine がリッスンするポートで、たとえば 80 や 443 です。Upstream は、SafeLine がリクエストをおくる、もとのアプリのアドレスです。HTTPS のアプリでは SSL オプションをえらびます。

メモはドメインとリッスンポートのペアごとにつくります。おなじドメインでもポートがちがえば、べつのらんにしてください。Upstream のポートは、バックエンドへのコネクションをあらわすため、パブリックなポートのらんにはかきません。

## 4. エンドポイントをひとつずつテストする

アプリをセットしたら、そのドメインが SafeLine のホストの IP アドレスをさすようにします。SafeLine は HTTP/HTTPS のリバースプロキシとしてリクエストをうけ、ゆるされたトラフィックをもとのアプリへおくります。

まずはふつうのページへアクセスし、ドメイン、ポート、アクセスしたときをメモします。そのあと、じぶんでコントロールでき、テストしてよいアプリだけで、ドキュメントのテストケースをひとつためします。ドキュメントには SQL インジェクション、XSS、パストラバーサル、コードインジェクション、XXE のサンプルがあり、ブロックページをぼうぎょのしるしとしてあつかっています。

いくつものエンドポイントをいっせいにテストせず、ひとつずつすすめると、あとでイベントとのつながりをたどりやすくなります。

## 5. アタックリストとメモをつきあわせる

テストのあと、コンソールのアタックリストをひらき、detail からイベントのくわしいデータをみます。メモしたエンドポイントとタイムスタンプをてがかりに、UI にでているデータをチェックしてください。

ここでは「UI でみえたこと」と「まだわからないこと」をわけてかきます。ドメインやポートがイベントにでていなければ、アプリのセットアップにそのフィールドがあるというだけで、イベントにもあるとはかぎりません。タイミングがちかいだけのイベントも、むりにひとつのポートへむすびつけないようにします。

レビューのメモには、いつからいつまでをみたか、どのイベントをみたか、どのデータをてがかりにしたか、なにがまだわからないかをのこします。ポートごとのイベントのかずをだすときも、つながりをたしかめられたイベントだけをカウントします。

## 6. うまくいかなかったときは、アクセスのながれをたどる

たとえば、`shop.example:443` を SafeLine でうけ、Upstream に `http://192.0.2.10:8080` をセットしたとします。レビューのメモに「8080 へのアタック」とだけかくと、バックエンドのポートをパブリックなポートととりちがえてしまいます。

このケースでは、メモを「ドメインは shop.example、リッスンポートは 443、Upstream は 192.0.2.10:8080」とわけます。ただし、これだけでイベントのポートまでたしかめられたことにはなりません。detail にあるデータとテストのメモで、どこまでつながりをたどれるかをチェックします。

テストしてもおもったようにならないときは、Domain、Port、SSL オプション、Upstream、ドメインがさす IP アドレスをもういちどみなおします。そのうえで、ゆるされたテストをひとつだけくりかえし、タイムスタンプをのこします。ブロックページがでないということだけで、どこにミスがあるかをきめつけないでください。

ドメインとポートごとのレビューをつづけるには、アプリのリストをそろえ、イベントでたしかめられることをていねいにひもづけることがたいせつです。わからないイベントはそのままメモにのこし、あとからたどれるレビューにしましょう。
