SafeLine WAF の LTS 環境から最新版へ移行する際、多くの運用者が「アップグレードコマンド一発」を期待します。しかし公式のデプロイガイドには、LTS から latest へその場で変換する移行コマンドは存在しません。LTS は `RELEASE=-lts` を指定した導入ライン、latest は `RELEASE` を空にして `IMAGE_TAG=latest` とし、latest リリースパスから compose ファイルを取得する導入ラインです。

ガイドによれば、LTS 版は 9.1.0-LTS（2025年8月14日）を最後にメンテナンスされません。LTS 利用者は最新版へのアップグレードを強く推奨されており、不安がある場合は新バージョン公開から1か月待ってから移行するのが公式の推奨です。

本記事では、既存のデータディレクトリの再利用を前提にせず、「検証済みの最新版導入」「新しいコンソール」「意図的な DNS 切り替え」の3つを軸にした実践手順をまとめます。

## 事前チェック

移行前にホストが公式の最小要件を満たすか確認します。

- `uname -m`: x86_64 または arm64 であること
- `docker version`: Docker 20.10.14 以上
- `docker compose version`: Docker Compose 2.0.0 以上
- `cat /proc/cpuinfo | grep processor`: CPU 1 コア以上
- `free -h`: メモリ 1 GB 以上
- `df -h`: ディスク 5 GB 以上
- `lscpu | grep ssse3`: CPU が ssse3 命令に対応していること

どれか一つでも満たさない場合は、そこで停止します。バージョン移行が依存関係の不備を解決してくれるわけではありません。

特に ARM サーバーの場合、手動導入では `ARCH_SUFFIX=-arm` を設定し、ガイド記載の ARM 用 Postgres イメージ（chaitin/safeline-postgres-arm:15.18）を使います。ARM 上で SafeLine を動かすには Pro ライセンスが必要で、Personal Edition は ARM 非対応です。`uname -m` で ARM と出た場合、ライセンスがなければ最新版への移行は Personal Edition の単純な置き換えになりません。

## 移行手順

1. **タイミングを決める。** 新リリースが公開から1か月以内なら、慎重に運用する場合は公式推奨どおり1か月待ちます。切り替え日、現在のインストールディレクトリ、管理ポートを記録します。本記事の例では MGT_PORT=9443、コンソール URL は `https://<safeline-ip>:9443/` です。

2. **アプリケーション一覧を作る。** SafeLine はリバースプロキシとして動作します。クライアントが最初に SafeLine に到達し、HTTP トラフィックのフィルタリングと監視を行い、許可した通信をアップストリームへ転送します。現行コンソールから、サイトごとに「Domain に使うドメイン・ホスト名・IP」「待受ポート」「SSL の有無」「アップストリームのアドレス」を控えます。レート制限、CAPTCHA チャレンジ、認証チャレンジ、動的保護を使っているサイトも書き出します。これらの設定は LTS ディレクトリと一緒に自動では移行しません。

3. **旧 LTS は新環境が実証されるまで残す。** 手動導入では /data/safeline を使い、SAFELINE_DIR にそのパスを設定します。古い Postgres データディレクトリや古い .env、検出トークンを新しいツリーへコピーせず、別ディレクトリか別サーバーを用意します。シークレットは新しい導入時に生成し直します。

4. **自動インストーラーを使う。** root シェルで `bash -c "$(curl -fsSLk https://waf.chaitin.com/release/latest/manager.sh)" -- --en` を実行します。URL のリリースパスは latest です。完了後、ガイドは Web UI を開くよう案内します。これは新しい latest 導入であり、LTS の切り替えスイッチではありません。

5. **手動導入が必要なら、compose ファイルを取得する。** Docker が未導入ならガイドのコマンドで導入し、SafeLine 用ディレクトリを作成して `https://waf.chaitin.com/release/latest/compose.yaml` をダウンロードします。.env をガイドの変数ブロックから作成し、`IMAGE_TAG=latest` と空の `RELEASE` を設定します。`RELEASE=-lts` は設定しません。x86_64 なら ARCH_SUFFIX は空のまま、Postgres は chaitin/safeline-postgres:15.18 を使います。MGT_PROXY はコンソールのプロキシ層を設定しない限り 0 にします。DETECTOR_MGMT_TOKEN、MGT_INTERNAL_TOKEN、DETECTOR_AES_KEY はガイドの od / tr コマンドで生成し、set_env 関数で保存して `chmod 600 .env` を実行します。リソース用ディレクトリを作成し、ソケットをリンクして `docker compose up -d` で起動します。初回起動には数分かかることがあります。

6. **新しいコンソールへサインインし、管理者パスワードを発行する。** `https://<safeline-ip>:9443/` を開き、`docker exec safeline-mgt resetadmin` を実行します。成功すると初期ユーザー admin と生成されたパスワードが表示されるので保存します。これは新規導入向けのコマンドであり、旧 LTS コンテナのパスワード復旧ツールではありません。

7. **アプリケーションを追加する。** Web 管理コンソールで「Applications」を開き、「Add Application」をクリックします。Domain、Port、Upstream を入力し、HTTPS サイトなら SSL にチェックを入れます。手順2の一覧の全行を繰り返します。

8. **DNS を切り替える。** 保存後、ドメインをこの最新版導入が動くサーバーの IP に解決させます。保護が有効になるのは、自分のドメインへのテストリクエストがブロックされ、コンソールの攻撃リストにイベントが表示されたときです。イベントの詳細画面を開き、ログが動くことを確認してから旧経路を廃止します。

9. **LTS ツリーを削除する。** 旧インストールディレクトリに入り `docker compose down` を実行し、データを消してよい場合のみ `rm -rf` でディレクトリを削除します。ガイドはこれらを完全削除として提示しており、バックアップではありません。絶対に新ディレクトリへ向けて実行しません。

## 失敗事例

ある環境では、`uname -m` を確認せずに latest の compose.yaml をダウンロードして起動し、後から ARM サーバーであることに気づきました。Personal Edition は ARM 非対応のため、コンソールは上がってもライセンス起因の不具合に直面し、結局 x86_64 の別ホストへ作り直すことになりました。移行前にアーキテクチャと最小要件を確認しておけば避けられた障害です。

## よくある疑問

**LTS から latest への公式移行コマンドはあるか。**

ありません。デプロイガイドには `RELEASE=-lts` の選択子、latest のインストーラー、手動 compose 手順、メンテナンス推奨が示されているだけです。未サポートのフラグ変更を当てにせず、上記の番号付き手順に従います。

**新リリースが不安な場合、どれだけ待てばよいか。**

公式の案内は明確で、LTS 利用者は最新版へのアップグレードを強く推奨され、懸念がある場合は新バージョン公開から1か月後にアップグレードします。この1か月はホスト検証とアプリケーション一覧の作成に使い、メンテナンスされないラインに居続けるための猶予ではありません。

**旧データディレクトリを新しい SAFELINE_DIR として再利用できるか。**

公式手順は「はい」とは言っていません。ディレクトリ作成、latest の compose 取得、環境変数記入、シークレット新規生成、権限設定、コンテナ起動を順に行うだけです。旧ディレクトリは新コンソールが一覧のサイトを配信できるまで変更せず、データ削除に確信が持ててから削除します。

**アプリケーションはすべて再登録が必要か。**

必要です。新コンソールではドメイン、待受ポート、SSL チェック、アップストリームを Applications から登録し、DNS を SafeLine サーバーへ向けます。テストリクエストを送り、ブロックと詳細画面を確認してから切り替え完了とします。

## まとめ

LTS から latest への移行は「アップグレード」ではなく「検証済みの別環境を作って切り替える」運用です。事前チェックを済ませ、アプリケーション一覧を書き出し、新しいシークレットで latest を構築し、DNS で切り替えて、旧環境は実証後に削除します。コンソールは `https://<safeline-ip>:9443/` にあります。
