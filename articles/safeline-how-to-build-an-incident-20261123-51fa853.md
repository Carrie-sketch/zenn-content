ウェブこうげきへのたいおうでは、「リクエストをブロックした」と「アプリやサーバーがぶじだった」をわけてかんがえます。ブロックのログは、そのリクエストをとめたことのてがかりです。それよりまえのしんにゅうや、べつのルートからのアクセスまで、ひていできるわけではありません。

この記事ではなく、このガイドでは、SafeLine WAF を HTTP トラフィックのチェックとブロックにつかいながら、アプリとホストのしらべかたをチェックリストにまとめます。ゴールは、アラートをけすことではなく、なにがおきて、どこまでひろがり、どうふっきしたかをせつめいできることです。

## 1. まず、だれがなにをするかをきめる

ほんばんのせっていをかえるまえに、インシデントのメモをつくります。つぎのチェックを、そのままテンプレートにしてください。

- [ ] たいおうリーダーとアプリのたんとうしゃをきめた
- [ ] トラフィックをせいげんできるひとをきめた
- [ ] ログなどのしょうこをほぞんするひとをきめた
- [ ] ホストめい、かんきょう、さいしょにきづいたじこくをのこした
- [ ] ログイン、けっさい、API など、えいきょうをうけるしごとをかきだした

アプリ、リバースプロキシ、にんしょう、OS、デプロイのログをそろえます。タイムゾーンと、とけいのずれもチェックしてください。じこくがずれていると、こうげきのリクエストとファイルのへんこうを、まちがってむすびつけてしまいます。

リクエストごとに、じこく、パス、HTTP メソッド、ステータス、つきあわせにつかえる ID をのこします。ボディにはパスワードやこじんのデータがふくまれることがあるため、むやみにチャットへはりつけません。もとのログはアクセスをせいげんしたばしょにほぞんし、いつ、だれがあつめたかもきろくします。

## 2. SafeLine のどうにゅうじょうけんをチェックする

SafeLine は、アプリのまえで HTTP トラフィックをフィルタリングし、モニタリングするセルフホストの WAF です。ウェブこうげきへのぼうぎょ、IP ベースのレートせいげん、アクセスせいぎょを、トラフィックのふうじこめにやくだてられます。ただし、サーバーがすでにしんがいされているかどうかは、べつにしらべます。

どうにゅうまえに、Linux、Docker 20.10.14 いこう、Docker Compose 2.0.0 いこうをチェックします。さいしょうリソースは CPU 1 コア、メモリ 1 GB、ディスク 5 GB です。アーキテクチャと CPU のじょうけんも、どうにゅうガイドでチェックしてください。ARM では Pro ライセンスがひつようで、Personal Edition はサポートされません。

ダッシュボードの URL は `https://<ip>:9443` です。かんりしゃのにんしょうじょうほうをあつかうてじゅんと、かんりアクセスをせいげんするてじゅんも、チェックリストにいれます。

## 3. アプリへのルートと、もどしかたをそろえる

SafeLine の Applications から Add Application をひらき、ドメイン、リッスンポート、アップストリームのアドレスをせっていします。HTTPS のアプリでは SSL オプションをゆうこうにします。そのうえで、アプリのドメインが SafeLine サーバーの IP をさすようにします。

DNS をかえるまえに、もとのせっていと、ロールバックのたんとうしゃをきろくしてください。へんこうのタイミングをあわせ、つぎをチェックします。

- [ ] TLS のしょうめいしょをただしくあつかえる
- [ ] ふつうのページがひらく
- [ ] ログインとログアウトができる
- [ ] じゅうような API のフローがとおる
- [ ] べつのホストめい、パブリック IP、ポートからオリジンへちょくせつアクセスできないかしらべた

オリジンにちょくせつとどくルートがあれば、WAF をうかいされるおそれがあります。こうせいがゆるすなら、オリジンへのアクセスを、そうていしたプロキシのルートにしぼります。じゅうようなフローがこわれたら、きめておいたてじゅんでもどし、エラーやログをのこします。

## 4. ブロックのテストを、アプリのログとつきあわせる

じぶんがほゆうする、またはテストをきょかされたアプリで、コントロールしたテストをおこないます。SafeLine のガイドにあるテストてじゅんをつかい、ブロックページとダッシュボードのこうげきリスト、そのしょうさいをチェックします。

ここでたいせつなのは、がめんだけでおわらせないことです。テストしたじこくとパスをひかえ、アップストリームのログとつきあわせます。ログがたりず、アプリやホストでなにがおきたかわからないなら、けっかは「ふめい」とします。「ログがないからあんぜん」とはしません。

## 5. てがかりにあわせて、たいおうをわける

チェックリストには、つぎのぶんきをかいておきます。

1. ブロックをかくにんし、ほかにしんがいのてがかりがない：サンプルをほぞんし、ねらわれたコンポーネントとパッチのじょうたいをチェックして、かんしをつづける。
2. あやしいリクエストがアプリまでとどいた：アプリのうごき、にんしょうイベント、ファイルのへんこう、ホストのプロセスをしらべる。
3. コードのじっこうや、しんにゅうをいじするしくみがうたがわれる：ひつようにおうじてワークロードをかくりし、しょうこをほぞんする。ろしゅつしたセッションやにんしょうじょうほうをむこうにし、ほかのシステムへのひろがりもしらべる。

みおぼえのないスクリプト、ふしぜんなアップロード、そのあとにつづくスクリプトへのアクセス、ウェブのワーカーからのコマンドじっこう、せつめいできないがいぶつうしんは、ウェブシェルをしらべるきっかけです。ひとつだけでだんていせず、しんらいできるデプロイのきろくとくらべます。

リクエストのりょうやボットによるアクセスがもんだいなら、レートせいげんや CAPTCHA もけんとうします。てきようごは、ふつうのユーザーのフローへのえいきょうをチェックします。これらをつかっても、パッチやホストのちょうさはひつようです。

### みじかいしっぱいれい

たとえば、ブロックのひょうじをみて、たんとうしゃがたいおうをおえたとします。しかし、オリジンのべつのポートがひらいたままで、そこへのアクセスと、みおぼえのないスクリプトをみおとしていました。

このケースでたりなかったのは、ブロックのかずではなく、ルートのチェックとホストのちょうさです。チェックリストには「オリジンへのべつルート」と「デプロイにないファイル」を、それぞれどくりつしたチェックとしていれます。

## 6. ふっきとクローズのじょうけんをきめる

アプリのたんとうしゃが、ねらわれたよわみをなおしたことをかくにんします。しんがいがあったなら、しんらいできるせいかぶつからふっきするか、システムをつくりなおします。ろしゅつしたシークレットをこうしんし、ふせいなアカウントやアクセスルートものぞきます。

- [ ] えいきょうのはんいと、ふうじこめのけっかをきろくした
- [ ] よわみへのたいおうをかくにんした
- [ ] ログインやじゅうような API がふっきした
- [ ] あやしいファイル、プロセス、つうしんがふたたびでていないかしらべた
- [ ] のこるふめいてんとリスクをきろくした
- [ ] のこるタスクに、たんとうしゃときげんをつけた

ダッシュボードがしずかになったことだけを、クローズのじょうけんにしないでください。たいおうリーダーが、はんい、ふうじこめ、しゅうふく、ふっきのチェック、のこるリスクをせつめいできるところまで、きろくをそろえます。
