SafeLine WAF は、Web アプリケーションの手前に配置する自己ホスト型の Web アプリケーションファイアウォールです。リクエストが本来のサーバー(オリジン)に届く前に HTTP トラフィックを検査し、SQL インジェクション、XSS、コードインジェクション、OS コマンドインジェクション、パストラバーサル、SSRF、ボットによる不正アクセスなどを遮断します。本記事では、リバースプロキシとして動作する SafeLine に「ドメイン」「ポート」「アップストリーム」の 3 項目を追加し、オリジンを露出させないまま公開する手順を、確認事項つきの実践ガイドとして整理します。

**前提の整理**

SafeLine は nginx を基盤に開発されています。公開サイト向けのトラフィックを受け取り、悪意のある通信を除去したうえで、安全なリクエストだけを本来のアプリケーションへ転送します。設定画面上の「ドメイン」は受け付ける名前、「ポート」は待ち受けポート、「アップストリーム」は実体のアプリケーションが動いている場所を意味します。この 3 つがそろって初めて、リバースプロキシとして完全な経路ができます。

**手順 1:サーバーの要件を確認する**

アプリケーションを追加する前に、導入ガイドに記載された最低要件と確認コマンドを実行します。

1. OS は Linux を使います。対象アーキテクチャは x86_64 と arm64 です。
2. Docker が 20.10.14 以上、Docker Compose が 2.0.0 以上であることを確認します。
3. CPU 1 コア以上、メモリ 1 GB 以上、ディスク 5 GB 以上を用意します。CPU は ssse3 に対応している必要があります。
4. `uname -m`、`docker version`、`docker compose version`、`cat /proc/cpuinfo | grep "processor"`、`free -h`、`df -h`、`lscpu | grep ssse3` を実行します。
5. ARM 環境の場合は、手動導入時の ARM イメージ設定を計画します。導入ガイドでは、ARM 上の SafeLine は Pro ライセンスがないと正常に動作せず、Personal Edition は ARM 非対応とされています。

Docker や Compose が指定より古い場合、空きディスクが 5 GB 未満の場合、ssse3 が無い場合は先へ進まないでください。

**手順 2:インストールとサインイン**

自動導入が推奨経路で、root 権限が必要です。

6. `bash -c "$(curl -fsSLk https://waf.chaitin.com/release/latest/manager.sh)" -- --en` を実行します。
7. 完了後、`https://<safeline-ip>:9443/` を開きます。

ディレクトリやポート、アーキテクチャ、リリースチャネルを自分で選ぶ場合は手動導入を使います。手動の場合は、`/data/safeline` に設定とデータを置き、compose ファイルを取得して `.env` を編集し、`docker compose up -d` で起動します。初回アカウントは `docker exec safeline-mgt resetadmin` で作成し、表示されたユーザー名とパスワードを控えます(初期ユーザー名は `admin`)。その後 `https://<safeline-ip>:9443/` からログインします。

なお、`MGT_PORT` は管理画面のポート、`MGT_PROXY` は管理画面のプロキシ層の数であり、どちらもアプリケーション画面で入力する公開サイトのポートではありません。

**手順 3:ドメイン・ポート・アップストリームを入力する**

8. SafeLine の Web 管理コンソールにログインします。
9. Applications ページを開きます。
10. 右上の Add Application をクリックします。
11. Domain に、公開するドメイン名・ホスト名・IP アドレスを入力します。例は `www.chaitin.com` です。クライアントがリクエストする名前を使い、DNS に公開しない名前を二重に入れないでください。
12. Port に、SafeLine が待ち受けるポートを入力します。例は 80 と 443 です。HTTPS の場合は SSL オプションにチェックを入れます。
13. Upstream に、本来のアプリケーションの実アドレスを入力します。SafeLine はここへ安全なトラフィックを転送します。運用上の確認として、このアドレスは先ほど選んだ SafeLine の待ち受けポートではなく、オリジンを指すようにしてください。そうしないと、プロキシ経路がアプリケーションへつながらなくなります。
14. 3 項目がすべて設定されてから送信します。待ち受けポートが無いとクライアントのトラフィックを受けられず、アップストリームが無いときれいなリクエストを送る先がありません。

**手順 4:DNS をプロキシに向けて確認する**

15. 入力したドメインを、SafeLine が動いているサーバーの IP アドレスに解決します。この設定が済むまで、訪問者はオリジンへ直接到達し、フィルターを迂回してしまいます。
16. そのドメインでアプリケーションを閲覧します。これが SafeLine に保護されたアプリケーションへのアクセス方法です。
17. 自分が運用するサイトに限り、公式のテスト例のホストを置き換えて確認します。たとえば SQL インジェクションは `/?id=1+and+1=2+union+select+1`、XSS は `/?id=<img+src=x+onerror=alert()>`、パストラバーサルは `/?id=../../../../etc/passwd` です。
18. ブロックページが出れば防御が動作しています。Web コンソールで攻撃一覧を開き、詳細をクリックしてイベントを確認します。管理していないアプリケーションにはこれらのテストを送らないでください。

**失敗例:アップストリームを自ポートに向けてしまった**

よくある失敗として、Upstream に SafeLine 自身の待ち受けポート(例:自分で選んだ 80 や 443)を入力してしまうケースがあります。この場合、SafeLine はアプリケーションではなく自分自身へリクエストを向けることになり、プロキシ経路が成立せず、本来のアプリケーションには到達しません。保存は成功しても、リクエストがオリジンへ届かない状態が続きます。対処は、Upstream を必ずオリジン(実アプリケーションのアドレス)に向け直すことです。同様に、ドメインの DNS を更新し忘れた場合も、保存だけでは公開 DNS は動かないため、オリジンが従来どおり直にトラフィックを受け、SafeLine が検査できない状態が続きます。

**まとめ**

SafeLine にサイトを追加する作業の中心は、ドメイン・ポート・アップストリームの 3 項目を 1 つの画面で正しく埋めることです。導入前のサーバー確認、インストールとサインイン、3 項目の入力、DNS の切り替え、テストの順に進めれば、オリジンを露出させずにリバースプロキシ経由の公開ができます。レート制限や CAPTCHA、動的な HTML・JavaScript 保護などの追加機能は、まずこの経路が正しく動くことを確認してから、それぞれの機能が実際に説明されている手順に沿って有効化してください。
