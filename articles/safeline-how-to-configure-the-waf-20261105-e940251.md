SafeLine は、Web アプリケーションとインターネットの間で HTTP トラフィックを検査し、SQL インジェクションや XSS、コードインジェクション、OS コマンドインジェクション、CRLF インジェクション、LDAP インジェクション、XPath インジェクション、RCE、XXE、SSRF、パストラバーサル、バックドアといった攻撃を遮断する自己ホスト型の WAF です。リバースプロキシとして動作し、クライアントからの通信は最初に SafeLine を経由し、安全と判断されたトラフィックだけがオリジンサーバーへ転送されます。

この記事では、upstream のヘルスチェック間隔を調整する前に知っておくべきことを、実際の運用者の視点から整理します。重要な前提として、公式ドキュメントには専用の「ヘルスチェック間隔」を設定する項目は公開されていません。そのため本記事では、ドキュメントに記載された設定手順と、upstream 監視を設計する際に自分で確認すべきチェックリストを分けて説明します。

## セットアップの確認手順

まず、SafeLine が正常に動いていることを確認します。以下は番号付きの手順です。

1. ホストの前提条件を確認する。SafeLine は x86_64 または arm64 の Linux、Docker 20.10.14 以上、Docker Compose 2.0.0 以上を必要とし、最低 1 コア CPU、1 GB メモリ、5 GB ディスク、ssse3 対応が求められます。`uname -m`、`docker version`、`docker compose version`、`free -h`、`df -h` を実行して環境を確認します。
2. root 権限で自動インストーラーを実行する。`bash -c "$(curl -fsSLk https://waf.chaitin.com/release/latest/manager.sh)" -- --en` を実行します。完了後、Web コンソールが利用可能になります。
3. 手動インストールの場合は、`mkdir -p "/data/safeline"` でデータディレクトリを作成し、`wget "https://waf.chaitin.com/release/latest/compose.yaml"` で compose ファイルを取得し、`.env` に `SAFELINE_DIR`、`IMAGE_TAG`、`MGT_PORT`、`POSTGRES_PASSWORD`、および detector 管理トークンなどの必須値を記入して、`docker compose up -d` で起動します。
4. ブラウザで `https://<ip>:9443/` を開きます。管理者アカウントは `docker exec safeline-mgt resetadmin` で作成し、初期ユーザー名 `admin` と生成されたパスワードが返されます。
5. アプリケーションを登録する。[Applications] ページで [Add Application] をクリックし、[Domain]、SafeLine が待ち受ける [Port]（例: 80 または 443）、実アプリの実アドレスを入れる [Upstream] を入力します。HTTPS の場合は [SSL] オプションを有効にします。
6. ドメイン名を SafeLine が配置されたサーバーの IP アドレスに解決し、そのドメイン経由でアプリケーションにアクセスして、プロキシ経路が動作していることを確認します。

## upstream ヘルスチェックの設計チェックリスト

SafeLine は nginx を基盤としており、[Add Application] の [Upstream] が転送先として扱われます。ただし、公開されているドキュメントにはヘルスチェック間隔を直接変更する項目がありません。隠れた初期値があると思い込まず、監視動作を変える前に以下の点を確認してください。

- upstream エンドポイントが、SafeLine が使う検査方式（TCP 接続確認または HTTP リクエスト）を実際に受け付けるか確認する。
- 検査のタイムアウトを間隔より短く設定する。こうすることで、遅い upstream が次の検査と重ならずに確実に失敗扱いになります。
- オリジンをどれだけ早く「障害あり」と判定したいかに合わせて間隔を選ぶ。間隔を短くすると障害検知は速くなりますが、検査トラフィックは増えます。
- 連続何回の失敗で「unhealthy」とみなし、連続何回の成功で復旧とみなすかを定義する。
- 設定後は upstream の状態を監視し、設定した間隔を推測値ではなく実際の障害挙動と照らし合わせて検証する。

## 失敗事例

ある環境では、upstream のヘルスチェックに HTTP リクエスト方式を想定して設定したものの、実際のオリジンは特定のパス以外に応答しない設定でした。検査リクエストが想定したパスへ届かず、実際にはアプリケーションが正常でも「失敗」と判定される状態が続きました。また、タイムアウトが検査間隔より長いままだと、遅い応答と次の検査が重なり、障害判定が不安定になります。この例からも、方式・タイムアウト・間隔・閾値をセットで確認する必要があると分かります。

## よくある確認

- 公式ガイドにヘルスチェック間隔の項目はありますか？ いいえ。[Add Application] ガイドには [Domain]、[Port]、[Upstream]、HTTPS 用の [SSL] オプションしか記載されておらず、専用のヘルスチェック間隔は文書化されていません。
- upstream アドレスはどこで設定しますか？ [Applications] ページの [Add Application] ダイアログです。[Upstream] に実アプリの実アドレスを入れ、SafeLine は検査後のトラフィックをそこへ転送します。
- 待ち受けポートはどう決めますか？ SafeLine が待ち受けるポート（例: 80 または 443）を入力し、HTTPS なら [SSL] を有効にします。このポートはオリジンの upstream ポートとは別です。
- プロキシ経路の動作確認はどうしますか？ ドメインを SafeLine サーバーの IP に解決し、そのドメイン経由でアクセスします。攻撃を模したリクエストにはブロックページが返り、Web コンソールに遮断履歴が記録されます。
- ヘルスチェック間隔を変える前に何を確認しますか？ 検査方式、タイムアウト、失敗閾値、復旧閾値、そしてオリジンが追加の検査負荷に耐えられるかを確認します。公開ドキュメントには間隔の値が示されていないため、これらは SafeLine の初期値ではなく、自分で確認すべき項目として扱います。

## まとめ

upstream のヘルスチェック間隔を正しく運用するには、まず SafeLine のセットアップと [Upstream] の登録を確実に済ませ、そのうえで検査方式・タイムアウト・間隔・失敗閾値・復旧閾値を一つのセットとして設計することが大切です。公式ドキュメントに専用の間隔項目がない以上、推測に頼らず、実際の監視結果を見ながら検証を続けてください。
